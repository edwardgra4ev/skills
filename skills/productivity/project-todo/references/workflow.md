# От требований к реализации

Этот workflow принадлежит project-todo. Для интервью используются отдельно установленные внешние навыки. Данные задач принадлежат рабочему
проекту; каталог установленного навыка содержит только инструкции.

## Найти проект и его соглашения

1. Используйте явно указанный пользователем проект. Иначе определите его по
   текущей рабочей директории и доступным правилам проекта (например, AGENTS.md).
   Для нескольких возможных проектов уточните выбор до зависимых действий.
   Расположение установленного навыка не определяет рабочий проект.
2. Используйте явно указанный реестр или путь из документации проекта.
   Иначе проверьте TODO.md в корне, docs/tasks/TODO.md, docs/FT/TODO.md
   и ссылки из существующего индекса документации. Это варианты поиска,
   а не требование создавать несколько реестров. При нескольких независимых
   реестрах уточните нужный; не объединяйте их автоматически.
3. Прочитайте существующий workflow проекта, если он указан в правилах или
   документах реестра. Сохраните его пути, ID, имена, язык, формат и статусы.
   Сопоставьте локальные статусы со смыслом таблицы ниже; не переписывайте
   реестр ради другого оформления. Неоднозначное соответствие уточните.
4. Если локального реестра нет, автоматически создайте пустой реестр при запуске
   навыка, в том числе при запросе только списка, без отдельного подтверждения.
   Используйте путь из соглашений проекта, иначе docs/tasks/TODO.md; создайте
   нужные каталоги. Явный запрет пользователя на запись имеет приоритет.
   Реестр содержит заголовок «Задачи проекта» и таблицу из раздела
   «Сохранить требования и план» без строк задач. Прочитайте созданный файл
   и сообщите его путь. Повторный запуск читает существующий реестр.
   Для пустого реестра выполните раздел [«Добавить первую задачу»](../SKILL.md#добавить-первую-задачу).
   Найденные требования и планы можно предложить перенести в реестр;
   автоматически записи из них не создавайте.
   Если проект использует внешний трекер вместо локального реестра, используйте доступную
   авторизованную интеграцию или запросите её данные; не изображайте доступ.
   Создание и изменение записей внешнего трекера требуют соответствующего поручения.

Для нового проекта без соглашений используйте docs/tasks/TODO.md,
docs/tasks/<slug>-requirements.md и docs/tasks/<slug>-plan.md.
ID по умолчанию — TASK-NNN, следующий свободный номер во всём реестре.
Зафиксируйте выбранные пути и формат в контексте плана, чтобы продолжение
не начинало поиск заново. При существующих именах и ID сохраняйте их.

## Сохранить требования и план

Перед записью найдите существующие документы той же задачи и продолжайте их.
Требования (ТЗ, ФТ, спецификация или соответствующий раздел общего документа)
содержат цель, пользователей, сценарии, границы, согласованные решения,
критерии приёмки и открытые вопросы. План содержит ссылку на требования,
этапы, затронутые компоненты, зависимости и проверки. Если проект ведёт
всё в одном документе, используйте его разделы вместо дублирующих файлов.

При поручении подготовить план сохраните сформированный черновик, даже если
интервью не завершено: неизвестное обозначьте явно, статус — draft или местный
эквивалент. Интервью о решении вне разработки не создаёт искусственную задачу.
Для нового реестра используйте столбцы:

| ID | Задача | Статус | Требования | План | Следующий шаг / блокер | Обновлено |
|---|---|---|---|---|---|---|

Ссылки в реестре относительны его каталогу, дата — YYYY-MM-DD.
При одном документе ссылки ведут на соответствующие разделы.
Добавляйте только реальные задачи. Сохраняйте завершённые и отменённые записи.
Статус храните в принятом реестре, прогресс этапов — в плане.
Добавляйте ссылки в существующий индекс документации по правилам проекта.

Подтверждение требований и критериев приёмки переводит задачу в ready.
Сохранение плана и статус ready сами по себе не запускают реализацию.

## Контекст продолжения

В требованиях и плане (или едином документе) сохраняйте краткий блок:
ID задачи, пути реестра и связанных документов, выбранный навык интервью
и причина выбора, текущий этап, ID открытых вопросов, команда продолжения.
Если документы отдельные, ID и выбранный навык должны совпадать.
Журнал вопросов и решений храните в требованиях; план ссылается на него.

- grill-me — уточнение требований, границ и плана.
- grill-with-docs — также определения предметной области, ADR и глоссарий.

Если для интервью навык ещё не выбран, выполните интерактивный выбор через [project-todo](../SKILL.md#интерактивно-выбрать-действие). Сохраните ответ пользователя; не приписывайте выбранному навыку создание старого документа.
При смене навыка сохраняйте решения и историю вопросов.
Если пользователь явно выбрал другой доступный навык, используйте его.
Если сохранённый навык недоступен, сообщите это и предложите установить зависимость по разделу [Внешние зависимости](../SKILL.md#внешние-зависимости). Замену согласуйте с пользователем.

Перед раундом восстановите контекст из документов. Каждый вопрос содержит
ID задачи и вопроса (например, TASK-001 / Q01), имя навыка, пути документов,
принятое решение, открытый выбор и рекомендацию. Используйте доступную форму
вопросов или обычный текст. Лимиты формы могут разбивать раунд на части;
ответов на зависимые решения дождитесь до следующего раунда.

Сохраняйте ID вопросов между раундами. Ответ фиксируйте с датой, решением
и затронутым этапом, затем обновляйте следующий шаг. Отсутствие ответа
не является согласием. При паузе сохраняйте открытые вопросы.
Для передачи в другой чат дайте команду с реальными ID и путями, например:
«Используй $project-todo: продолжи подготовку ТЗ TASK-001 через grill-me по указанным требованиям и плану с вопроса Q02». Подставьте конкретные документы вместо общего описания.

## Статусы по умолчанию

| Статус | Значение |
|---|---|
| draft | Требуется уточнение решений или подтверждение плана. |
| ready | Требования и план согласованы, можно выбирать для реализации. |
| in_progress | Реализация поручена и начата, прогресс записан в плане. |
| blocked | Есть конкретное препятствие и следующий шаг для его устранения. |
| done | Выполнены критерии приёмки и обязательные проверки. |
| cancelled | Пользователь отменил задачу, причина записана. |

Незавершённые — draft, ready, in_progress и blocked.
Неизвестные статусы показывайте как требующие уточнения.
Исчезновение документа не означает завершение. Пропущенная обязательная
проверка не позволяет ставить done. Деплой требуется для done, только если
он входит в критерии приёмки. Причина blocked должна быть конкретной.

## Начать или продолжить выбранную задачу

Выбор задачи в TODO определяет контекст. Выбор действия «Разработка по готовому ТЗ» в project-todo или прямое поручение разработать разрешает реализацию именно этой задачи. Выбор grill разрешает подготовку ТЗ, но не запуск кода. При просмотре списка создаётся только отсутствующий пустой реестр; существующие задачи, документы и статусы до выбора действия не меняются.

Прочитайте требования и план полностью, проверьте актуальность относительно
кода. Для draft завершите уточнения и получите подтверждение решений;
для blocked проверьте, устранено ли препятствие. Противоречия и недостающие
требования согласуйте до зависимых изменений. Небольшую задачу без отдельных
документов можно описать в существующей записи по соглашениям проекта;
не придумывайте недостающие требования или результаты проверок.

Для ready без новых противоречий начните реализацию. Для in_progress
продолжите первый незавершённый этап. Соблюдайте локальные правила веток,
изменений и проверок; если Git не используется, не создавайте репозиторий
ради этого workflow. Сохраните существующие пользовательские изменения.
Поставьте in_progress при начале реализации и запишите рабочую ветку,
если она применима.

После этапа обновляйте прогресс и следующий шаг. Перед done проверьте каждый
критерий приёмки и запишите результаты, включая ограничения проверки.
Публикация, merge, релиз и деплой выполняются только в пределах поручения
пользователя и правил целевого проекта; выбор задачи сам по себе их не разрешает.
